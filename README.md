# ESP32-CAM: живой просмотр на OLED + ASCII-арт в Telegram

Плата показывает картинку с камеры на дисплее, по нажатию кнопки делает
снимок, переводит его в псевдографику и отправляет в Telegram. Заодно
поднимает свою точку доступа с веб-страницей — арт видно и без интернета.

---

## Состав

```
esp32cam_ascii_bot/esp32cam_ascii_bot.ino   боевой скетч
esp32cam_diag_web/esp32cam_diag_web.ino     диагностика пайки через веб-страницу
vps/docker-compose.yml                      перенаправитель Telegram на сервере
vps/nginx.conf                              его конфиг
vps/push.sh                                 выкатка на VPS одной командой
```

## Железо

| что | куда |
|---|---|
| OLED SSD1306, SDA | IO14 |
| OLED SSD1306, SCL | IO13 |
| OLED VCC | 3.3 В (не 5 В: пины процессора не терпят больше 3.6 В) |
| кнопка | IO2 и GND, по диагонали |
| питание | 5 В на пин 5V, повышайка MT3608 |
| земля | GND рядом с 5V или рядом с IO0 |

Допустимое питание на пине 5V: **4.6–6 В**. Нижняя граница — падение на
стабилизаторе AMS1117 (ему нужно на 1.1 В больше, чем он отдаёт).
Верхняя — нагрев. Норма 5.0–5.1 В.

Пин с подписью GND рядом с U0T на многих платах **не земля** — прозвонка
до остальных GND молчит. Ничего к нему не подключать.

Вспышка из кода убрана: GPIO4 переводится в выход и прижимается к земле
первой же строкой `setup()`. Короткое свечение при подаче питания убрать
нельзя — эти доли секунды работает встроенный загрузчик, скетч ещё не
запущен, и пин ничем не управляется.

## Что настроить в скетче

Всё в шапке файла:

```c
#define WIFI_SSID        "..."
#define WIFI_PASS        "..."
#define TG_BOT_TOKEN     "..."          // из BotFather
#define TG_CHAT_ID       "..."          // свой id
#define TG_VIA_PROXY     1              // 1 = через VPS, 0 = напрямую
#define TG_PROXY_HOST    "ВАШ_IP"
#define TG_PROXY_PORT    8099
#define CAM_VFLIP        0              // ориентация картинки
#define CAM_HMIRROR      1
#define ART_W            48             // ширина арта в символах
#define ART_H            16             // высота арта в строках
#define TG_INVERT        1              // 1 = тёмная тема Telegram
```

Размер арта выбирается по тому, где его смотрят:

| `ART_W` × `ART_H` | где |
|---|---|
| 32 × 11 | телефон, строки не переносятся |
| 48 × 16 | компьютер |
| 64 × 22 | компьютер, самый подробный |

Ориентация подбирается опытным путём, наведи камеру на текст:

| что видишь | что менять |
|---|---|
| читается нормально | ничего |
| вверх ногами | оба значения на противоположные |
| зеркально, строки на месте | только `CAM_HMIRROR` |
| на голове, но не зеркально | только `CAM_VFLIP` |

## Перенаправитель Telegram на VPS

Зачем: сеть блокирует TCP до `api.telegram.org` — DNS отвечает,
соединение не встаёт. Обход не на плате, а на сервере: плата шлёт обычный
HTTP на VPS, nginx переписывает запрос в HTTPS и отправляет в Telegram.
Для платы это тот же Bot API, меняется только адрес.

Побочный плюс: HTTPS съедал на плате около 40 КБ оперативной памяти и
время на рукопожатие. Прошивка похудела с 1174 КБ до 1084 КБ.

### Развернуть

```
bash vps/push.sh
```

Скрипт проверит свободен ли порт, зальёт файлы, поднимет контейнер и
прогонит проверку с двух сторон — изнутри сервера и снаружи.

```
bash vps/push.sh --check    только проверить
bash vps/push.sh --down     остановить и убрать
```

Хост, ключ и порт задаются переменными окружения: `ESP32_HOST`,
`ESP32_KEY`, `PROXY_PORT` (в скрипте лежат заглушки).

### Как проверяется

Скрипт шлёт **заведомо неверный** токен и ждёт `401`. Этот ответ приходит
от самого Telegram, то есть доказывает, что запрос дошёл и вернулся.
Настоящий токен в проверке не участвует и на сервере не хранится вообще —
плата присылает его сама в адресе запроса.

### Почему не станет открытым ретранслятором

nginx пересылает только пути, начинающиеся на `/bot<НОМЕР_БОТА>:` — номер
бота не секретный, но без токена туда всё равно не постучаться. Всё
остальное отдаёт 404.

Если сменишь бота — поправь номер в `nginx.conf` и в `push.sh`
(`BOT_ID`). При `/revoke` в BotFather номер не меняется, менять нужно
только `TG_BOT_TOKEN` в скетче.

### Развёрнутое состояние

```
проект:    esp32proxy          отдельный, соседи по VPS не задеты
контейнер: esp32_tgproxy       nginx:1.27-alpine
порт:      8099 -> 80
подсеть:   172.29.0.0/16       (заняты: 172.17-172.20, 172.28)
```

Порт открывать через ufw не нужно: Docker публикует порты своими
правилами в цепочке `DOCKER-USER`, она отрабатывает раньше ufw.

## Диагностика пайки

Если экран не загорается или плата ведёт себя странно — прошей
`esp32cam_diag_web`. Он поднимает точку доступа **ESP32-DIAG**
(пароль `12345678`) и отдаёт отчёт на `http://192.168.4.1`.

Что показывает:

- причину последней перезагрузки (просадка питания, сторожевой таймер);
- уровень каждого пина с подтяжкой вверх и вниз;
- сканирование шины I2C в обоих порядках проводов;
- состояние кнопки и наличие перемычки между IO2 и IO4.

Как читать таблицу пинов:

| показания | что значит |
|---|---|
| `вверх=1 вниз=0` | пин свободен, снаружи ничего не подключено |
| `вверх=0 вниз=0` | пин замкнут на землю |
| `вверх=1 вниз=1` | пин притянут к плюсу снаружи |

Для линий I2C `вверх=1 вниз=1` — это **норма**: так проявляются
подтягивающие резисторы модуля дисплея, то есть он запитан и провода
целы. Пустой скан при живых линиях означает, что дисплей не отвечает.

Сканирование не запускается, если линия прижата к земле: драйвер I2C
в этом случае зависает намертво вместе со всей платой.

Кнопка «Пересканировать» повторяет проверку без перепрошивки — удобно
шевелить провода и сразу видеть результат. Плавающий контакт только так
и ловится.
